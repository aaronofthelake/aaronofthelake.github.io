Resetting a Grok Bot is easy. Keeping its memory isn't.

Aaron Lake · Badlands Technologies

Resetting a Grok Bot chat is how you stop paying to reread a long history, but the bot's memory doesn't move with it on its own. We built a reset process for our fleet: full chat backups, searchable bot-memory history, a short written handoff, and routines that keep their exact on or paused state. Along the way we learned that in-app memory can't be exported, and that our readiness check had passed against a stale copy.

Why long chats need resetting

Grok Bot sends the whole chat, plus instructions, memory and tool schemas, on every turn, and only summarizes near the context limit. So a one-line reply in a 130k chat costs about as much as a long message in that chat.

"…isn't intended behavior." (Cursor staff, on Grok Bot sending the full transcript every turn, Cursor forum)

Source: Cursor forum thread

Caveat: how the app selects context is our inference from usage data, not from app internals.

What long chats cost us

Oct 23, 2026, points by cost type (1 point = 1% of the Grok Bot weekly allowance):

  • Rereading context (cache reads): 16.0 pts
  • Cache writes, incl. 76 cold resends: 3.5 pts
  • Other fresh input: 0.6 pts

On Oct 23, 2026, our Grok Bot fleet used 20 points of its weekly allowance in one day: about 200 chat turns across 8 bots, with most chats sitting at 80k to 140k tokens of context.

Breaking the day down from the usage export, there was no runaway loop and no stuck routine. It was volume, and almost all of it was rereading. Requests made at 60k context or more accounted for 16.2 of the 20 points. About 1.9 points came from 76 "cold cache" requests, where a chat sat idle and then re-sent its whole 50k to 140k context. Output tokens barely registered.

In tokens, 1 point is about 9.5M cache-read tokens or about 2.5M fresh input tokens. That is an estimate (±20%), from a regression on our own usage data.

The obvious fix is to reset long chats. The reason nobody does is just as obvious: the bot forgets what you were working on.

What we built: bot-memory

bot-memory makes a reset cheap to recover from. It has two parts.

  1. A local, per-bot history cache. A small script copies each bot's chat history into a local SQLite database with full-text search every 15 minutes. It is read-only against the source, uses no AI and costs zero tokens. Each sync takes about 0.05 to 2 seconds. The cache holds 7,140 messages, matching the source with 0 missing and 0 duplicates.
  2. An MCP lookup server with four tools: get_checkpoint (latest saved state plus recent session digests), get_history (ranked search), get_messages (full text of specific messages) and save_checkpoint. Every output has a hard size cap, so a lookup costs a few thousand characters, not the whole chat.

The key point: A lookup server by itself saves nothing, because the chat still rereads its own history every turn. The savings come from the reset; bot-memory removes the reason not to reset.

We couldn't reset a chat in place, so for us a "reset" meant a new bot that replaces the old one. bot-memory links the new bot to its predecessor, so its lookups cover the old chat's full history as if it were its own. Bots can also be excluded entirely by config: excluded history is never copied, and every tool refuses it.

The first real reset: Oct 24, 2026

On Oct 24, 2026, we reset our usage-tracking bot, TokenAgent, a long-running chat with weeks of history.

  1. Back up first. A fresh, checksummed backup of the chat history is a required first step, and no reset happens without the owner's approval.
  2. Write the handoff. The outgoing chat wrote its own handoff (routines word for word, memory facts, open work, benchmark numbers and their gaps) and saved two checkpoints to bot-memory.
  3. Create and link the new bot. Its first get_checkpoint call showed 279 messages from its predecessor and 0 of its own. The chat history carried over in full; the bot's in-app memory was another story (see below).
  4. Move routines without double runs. The new chat recreated its scheduled routine word for word; the old chat paused its copy (paused, not deleted), so it never ran twice.
  5. Carry over memory. 34 memory facts copied word for word from the bot's own self-report, since memory lives on the app server, plus a short pinned recap and a lookup rule: check bot-memory first, never guess.
  6. Quiz the new bot. Four questions about past decisions, numbers and file locations: 4 of 4 correct, 0 made up, from 3 lookups, graded against the bot's saved pre-reset checkpoints.
  7. Keep the old chat. Renamed and hidden, not deleted.

What the reset cost: the day's burn was about 10 points, and the one-time reset and handoff work was about 2.4 of those. That is an estimate with medium confidence, since other bots shared some of those hours.

What moving a bot's memory taught us

The switch worked, but the days after it taught us more than the build did. If you run an agent fleet, these are the four things we would tell you first.

  1. In-app memory may not be exportable, so plan for that before you switch. The memory files on our box turned out to be a stale Oct 23 copy whose content stopped around Sept 15. Newer memory lived only on the app server, with no export tool. Our trading bot rebuilt its handoff by recalling its own server memory, which returns about 14 results per query, and reached 75 of its 93 profile facts; 18 could not be recovered that way.
  2. A check is only as good as what it compares against. Our readiness check passed because it compared the handoff to that stale copy, so the switch was called ready when memory after Sept 15 had never been verified. Before you trust a green check, confirm its reference is current and complete.
  3. Keep it simple. Our process grew into huge copied handoffs and repeated re-checks, and that cost days. Where we landed on Oct 27: full chat backups, searchable bot-memory history, and a short written handoff. No hidden archive bots.
  4. Carry routines over with their exact state. A routine that was on stays on, and a paused routine must never come back on. Our handoff format now requires an explicit enabled or paused state for every routine, and the switch checks that the old bot's copies are paused.

The takeaway: The memory you can see on disk may not be the memory your bot is using. Verify against the live source before you call a switch ready.

Lessons from the build

  1. Don't code inside bot chats. On Oct 23, one bot doing coding in chat cost about 4 to 5.5 points while the separate Cursor Models allowance sat at 3%. Tip for legacy Cursor plan users: code in local Cursor (CLI or editor) on a Grok model, which bills to Cursor Models. We built bot-memory itself this way.
  2. Set up the Cursor CLI on day one. When we needed ours, the stored login had lapsed and the newest version wouldn't start on an older macOS. Our bot template now includes a setup check that fails if the CLI isn't installed, signed in and set to a Grok model.
  3. Phone-only users have no local fallback. Our inference from the default setup: coding happens in the bot chat or its cloud instance, so phone-only users have no local Cursor to move it to.
  4. Measure before you cut. We found the coding-in-chat cost only by measuring usage per bot. The fix wasn't using the bots less; it was where the work ran and how long the chats got.
  5. Plan for the boring bugs: duplicate rows from the source re-indexing (1,384 collapsed), a search miss on exact numbers, a tool list cached by server name, and stale server processes. Each is now covered by a test or a deploy step.

What's next

We'll run the after-benchmark, reset more of our longest chats, and share the results in a follow-up post. We plan to release the code as a Grok Bot template, so other fleets can use the same reset process. If you run a bot fleet and have measured context cost differently, I'd like to compare notes.
